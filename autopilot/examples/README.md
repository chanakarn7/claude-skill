# ตัวอย่างไอเดีย (intake) สำหรับ autopilot

| ไฟล์ | ขนาดงาน | ใช้ทดสอบอะไร |
|---|---|---|
| `expense-tracker.md` | เล็ก เขียนแบบข้อความอิสระ (ไม่มีหัวข้อ) แอป client-only ไม่มี server | วงจรเต็มแบบถูกที่สุด · การที่ agent ต้องเดาเกือบทุกอย่างแล้วจดใน `DECISIONS.md` |
| `meeting-room-booking.md` | กลาง **กรอกครบทุกหัวข้อ** แอปที่มี server + ฐานข้อมูล สองบทบาท deploy ไป Raspberry Pi | stack มาตรฐาน (Next + Nest + Prisma + PostgreSQL + Docker), สคริปต์เดโม (`seed:demo`, `npm run demo`), บทบาทและสิทธิ์, ข้อจำกัดของเครื่อง (arm64, RAM 4 GB, HTTP ไม่มี HTTPS), หน้า dashboard + กราฟ, กฎธุรกิจที่ต้องมี test แน่นอน (จองชน, จองซ้ำ) |
| `expense-tracker-run/` (ที่ root ของ repo: `examples/expense-tracker-run/`) | ผลรันจริงถึงขั้น proto ของ `expense-tracker` | ทดสอบต่อจากกลางทางโดยไม่ต้องเสียงานขั้น BA ถึง proto ใหม่ ดู README ของมัน |

เริ่มรัน:

```bash
autopilot start autopilot/examples/meeting-room-booking.md ~/work/room-booking
```

ก่อนเริ่ม `autopilot start` จะพิมพ์ **Intake check** ให้ดูว่าหัวข้อไหนกรอกแล้ว (GIVEN) ปล่อยให้ AI เลือก (DELEGATED) หรือขาด (MISSING) รันเองได้ด้วย `node autopilot/templates/check-intake.mjs <ไฟล์>` (ไม่ใช้ token)

## intake ต้องมีข้อมูลอะไร และใครใช้

ไฟล์เดียว บันทึกเป็น `docs/IDEA.md` ในโปรเจกต์ ทุก agent อ่านจากที่นี่ ถ้าหัวข้อไหนขาด agent จะเดาและจดไว้ใน `docs/DECISIONS.md` ให้คุณเห็นที่ Gate 1 หัวข้อ ★ คือหัวข้อที่เดาแล้วเสี่ยงที่สุด

| หัวข้อ | ใส่อะไร | ใครใช้ และถ้าขาดจะเกิดอะไร |
|---|---|---|
| **1. Requirement ★** | ปัญหา · ผู้ใช้และบทบาท · "ต้องทำได้" เป็นข้อๆ · "ไม่ต้องมี" · กฎธุรกิจที่มีตัวเลข · ข้อมูลเดิม | BA ทำ PRD และ user story จากนี้ Reviewer ตรวจว่าทุกข้อกลายเป็น story ขาด = ขอบเขตผิด · ไม่มี "ไม่ต้องมี" = BA ตัดขอบเขตเอง · กฎที่ไม่ใส่ตัวเลข = agent เดา และเทสต์จะเทียบกับค่าที่เดา |
| **2. เกณฑ์ผ่าน ★** | เงื่อนไข "ใช้ได้จริง" **เป็นตัวเลขที่ทดสอบได้** (กี่แตะ กี่วินาที กี่คน กี่แถว) | BA ใส่ใน PRD · SA ทำตาราง Acceptance verification · QA ทดสอบเป็นข้อๆ ขาดตัวเลข = QA ตัดสิน pass/fail ไม่ได้ |
| **Look & feel** (ถ้ามี UI) | ผู้ใช้/อุปกรณ์ · ความรู้สึกและที่ไม่เอา · เว็บอ้างอิง + anti-reference · ลำดับความสำคัญของหน้า · สี/ฟอนต์/ธีม · ความหนาแน่น · กราฟที่ต้องมี · ข้อมูลตัวอย่าง · เกณฑ์ผ่านด้านภาพ | Designer, proto, QA (visual pass) ขาด = designer เสนอ 3 ทิศทางให้เลือกที่ Gate V (ปลอดภัยแต่ช้ากว่า) · "ให้ AI เสนอ 3 แบบ" ใช้ได้ |
| **Tech stack & ข้อจำกัด ★** | ต้องใช้ · **ห้ามใช้** · ของเดิมที่ต้องต่อ · Auth · integration ภายนอก · ภาษา UI · ขนาดงาน (ผู้ใช้/ข้อมูล) · เบราว์เซอร์ | SA เลือก stack (ทับค่าเริ่มต้นใน `stack.md`) · Dev ทำตาม ขาด "ห้ามใช้" = agent อาจเลือกบริการคลาวด์ที่มีค่าใช้จ่าย · ขาด Auth/Integration = เดา |
| **เซิร์ฟเวอร์และการ deploy ★** (ถ้า deploy) | ปลายทาง · CPU arch · RAM · ดิสก์ · Docker · **เครือข่าย (โดเมน/HTTPS/LAN)** · ใครดูแลและ deploy ยังไง · backup/secret · งบ | SA ตรวจว่า stack รันบนเครื่องนี้ได้ (ตัวเลข `Capacity & fit`) · DevOps ทำไฟล์ deploy ขาด arch/RAM = SA เช็กความพอดีไม่ได้ · ขาดข้อมูล HTTP/HTTPS = อาจใช้ API ที่ใช้ได้เฉพาะ HTTPS แล้วพังบน LAN |
| **การตัดสินใจที่ล็อกแล้ว** | สิ่งที่ agent ห้ามเปลี่ยน | ทุก agent และ reviewer (ถ้า agent เปลี่ยน = BLOCK) |
| **ถ้าไม่แน่ใจ ให้ agent...** | ให้เดาและจด หรือ **หยุดถามที่ Gate 1** ในเรื่องใดบ้าง (เงิน สิทธิ์ ข้อมูลส่วนบุคคล) | BA ใส่หัวข้อที่ขอให้หยุดถามไว้ใน Open questions แทนที่จะตัดสินใจเอง |

## ข้อควรระวังในการเขียน intake ให้ agent รันได้ดี

- **กฎที่มีตัวเลขต้องไม่กำกวม** reviewer จะตรวจตัวอย่างและตัวเลขด้วยการคำนวณจริง และตีกลับถ้ามีตัวอย่างผิด (วันที่ผิดวัน ยอดไม่ลงตัว) หรือกฎแบบ "A หรือ B" ที่เทสต์ให้ผลแน่นอนไม่ได้ ตัวอย่างใน `meeting-room-booking.md`: ช่วงเวลา "เริ่มรวม สิ้นสุดไม่รวม", การจองซ้ำที่ชนให้ "ข้ามและแจ้ง", การจองซ้ำที่เกินเพดาน 10 รายการให้ "ไม่สร้างทั้งชุด"
- **ตัวเลขใน เกณฑ์ผ่าน ต้องสอดคล้องกับขนาดงาน** (ตัวอย่าง: โต 7,500 การจองต่อปี ทดสอบที่ 10,000) เพราะ SA คำนวณ Capacity & fit จากตัวเลขเหล่านี้
- **เขียนข้อจำกัดของเครื่องจริง** เช่น "ไม่มี HTTPS" หรือ "RAM 4 GB" เป็นข้อมูลที่ทำให้ SA/dev เลือกสิ่งที่รันได้ ไม่ใช่รายละเอียดเสริม
- **อยากทดสอบทางหยุดถามที่ Gate 1** ใส่เรื่องที่เป็นการตัดสินใจของคนไว้ใน "ถ้าไม่แน่ใจ" ตัวอย่างนี้ตั้งใจเว้นสองเรื่องไว้ (ตารางแสดงชื่อผู้จองให้ทุกคนเห็นไหม · ใครแก้การจองแทนกันได้) และคาดหวังว่า reviewer ที่ Gate 1 จะตรวจว่าสองเรื่องนี้อยู่ใน Open questions ไม่ใช่ถูกตัดสินเงียบๆ
- ไม่รู้ข้อไหน ให้เขียนว่า "ไม่รู้" หรือ "ให้ AI เลือก" ดีกว่าเว้นว่าง เพราะตัวตรวจ intake แยก "มอบให้ AI" ออกจาก "ลืมกรอก" ได้
