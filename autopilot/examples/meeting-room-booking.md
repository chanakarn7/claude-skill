# ไอเดีย: ระบบจองห้องประชุมในออฟฟิศ

> ตัวอย่างเต็มรูปแบบของ intake (ดู `idea-template.md` และ `examples/README.md`) รันด้วย `autopilot start examples/meeting-room-booking.md <โฟลเดอร์โปรเจกต์>`

## 1. Requirement ★
- **ปัญหา / เป้าหมาย:** ออฟฟิศมี 25 คนและห้องประชุม 3 ห้อง ตอนนี้จองกันในกลุ่ม LINE จึงจองชนกันประมาณสัปดาห์ละ 3 ครั้ง และไม่มีใครรู้ว่าห้องไหนว่างตอนไหน ต้องการระบบจองกลางที่ **จองชนกันไม่ได้เลย** และดูห้องว่างได้ในไม่กี่วินาที
- **ผู้ใช้:**
  - พนักงาน 25 คน (ราว 70% เปิดบนมือถือ ที่เหลือบนเดสก์ท็อป) จองห้อง ดูตาราง ยกเลิกของตัวเอง
  - แอดมินออฟฟิศ 2 คน (เดสก์ท็อป) จัดการห้อง ผู้ใช้ วันหยุด และยกเลิกการจองของใครก็ได้
- **ต้องทำได้ (ทีละข้อ):**
  1. เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน แอดมินเป็นคนสร้างบัญชีและตั้งรหัสผ่านเริ่มต้น ผู้ใช้ต้องเปลี่ยนรหัสผ่านตอนเข้าครั้งแรก
  2. ดูตารางห้องประชุมแบบรายวัน (ทุกห้องเทียบกัน) และรายสัปดาห์ (ห้องเดียว) ช่องว่างและช่องที่ถูกจองมองออกทันที
  3. จองห้อง: เลือกห้อง วัน เวลาเริ่มและสิ้นสุด หัวข้อการประชุม และจำนวนผู้เข้าร่วม ถ้าเวลาชนกับการจองอื่นของห้องเดียวกัน หรือผู้เข้าร่วมเกินความจุ ต้องบอกเหตุผลและจองไม่ได้
  4. จองซ้ำรายสัปดาห์ (วัน-เวลาเดิมของทุกสัปดาห์ไปอีก 2 ถึง 8 สัปดาห์)
  5. แก้ไขหรือยกเลิกการจองของตัวเองก่อนเริ่ม แอดมินยกเลิกของใครก็ได้ทุกเวลา
  6. หน้า "การจองของฉัน" แสดงการจองที่กำลังจะมาถึงเรียงตามเวลา
  7. แอดมินจัดการห้อง (ชื่อ ความจุ อุปกรณ์ เปิดหรือปิดใช้งานชั่วคราว) จัดการผู้ใช้ (สร้าง ปิดบัญชี รีเซ็ตรหัสผ่าน) และวันหยุดบริษัท (จองไม่ได้ในวันหยุด)
  8. หน้า "การใช้ห้อง" สำหรับแอดมิน: เปอร์เซ็นต์การใช้งานของแต่ละห้องในสัปดาห์ที่เลือก
- **ไม่ต้องมี (รอบนี้):** แจ้งเตือนทางอีเมลหรือ LINE · ซิงก์ปฏิทิน Google/Outlook · เช็กอินด้วย QR · ขั้นตอนอนุมัติการจอง · การชำระเงิน · แอปมือถือเนทีฟ
- **กฎธุรกิจที่รู้แล้ว:**
  - เวลาทำการ 08:00–18:00 วันจันทร์ถึงศุกร์ ไม่รวมวันหยุดบริษัท แบ่งเป็นช่วงละ 30 นาที (ห้องหนึ่งมี 20 ช่องต่อวัน) เขตเวลา Asia/Bangkok
  - จองได้นานสุด 4 ชั่วโมงต่อครั้ง ล่วงหน้าได้สูงสุด 60 วัน จองย้อนหลังไม่ได้
  - ช่วงเวลาเป็นแบบ "เริ่มรวม สิ้นสุดไม่รวม": จอง 10:00–11:00 กับ 11:00–12:00 **ไม่ถือว่าชน**
  - พนักงานหนึ่งคนมีการจองที่ยังไม่เริ่มพร้อมกันได้ไม่เกิน 10 รายการ (การจองซ้ำนับแยกรายครั้ง)
  - ถ้าการจองซ้ำจะทำให้จำนวนการจองที่ยังไม่เริ่มของคนนั้นเกิน 10 รายการ ให้ **ไม่สร้างเลยทั้งชุด** และบอกว่าจองเพิ่มได้อีกกี่รายการ
  - ผู้จองยกเลิกหรือแก้ของตัวเองได้ถ้าเหลืออย่างน้อย 15 นาทีก่อนเริ่ม แอดมินทำได้ทุกเวลา
  - จองซ้ำรายสัปดาห์: วันไหนชนกับการจองอื่นหรือตรงวันหยุด ให้ **ข้ามวันนั้นและแจ้งรายการวันที่ข้าม** ไม่ล้มทั้งชุด
  - ห้อง (ชื่อ ความจุ อุปกรณ์): A "ห้องแสงอรุณ" 12 คน จอและไวท์บอร์ด · B "ห้องสายลม" 6 คน จอ · C "ห้องเล็ก 1" 4 คน ไม่มีอุปกรณ์
  - ปิดใช้งานห้องไม่ลบการจองที่ผ่านมา และห้ามปิดห้องที่ยังมีการจองในอนาคตโดยไม่แจ้งแอดมินว่ามีกี่รายการ
- **ข้อมูล:** ไม่มีข้อมูลเดิมให้นำเข้า ใช้ข้อมูลตัวอย่างตามหัวข้อ Look & feel
- **ไฟล์/ของเดิมที่ต้องใช้:** ไม่มี (ไม่มีโลโก้ ไม่มีไฟล์ตัวอย่าง)

## 2. เกณฑ์ผ่าน ★
1. พนักงานจองห้องได้ภายใน **4 แตะ** บนมือถือ นับจากหน้าตารางรายวัน (แตะช่องว่าง → ใส่หัวข้อ → ยืนยัน)
2. **ไม่มีการจองชนกัน:** เมื่อสองคนจองห้องและช่วงเวลาเดียวกันพร้อมกัน สำเร็จคนเดียวและอีกคนได้ข้อความว่าชน ทดสอบอัตโนมัติ 100 รอบต้องไม่เคยชน
3. หน้าตารางรายวันโหลดเสร็จภายใน **1 วินาที** บน Raspberry Pi 4 ผ่านเครือข่ายในออฟฟิศ ด้วยข้อมูล 10,000 การจอง
4. รองรับผู้ใช้พร้อมกัน 25 คน
5. จองซ้ำ 8 สัปดาห์ที่มีวันหยุดหนึ่งวัน ต้องได้การจอง 7 รายการและแจ้งว่าข้าม 1 วัน (ระบุวันที่)
6. ข้อมูลไม่หายเมื่อรีสตาร์ทเครื่อง Raspberry Pi
7. ใช้งานได้บน Safari บน iPhone, Chrome บน Android และ Chrome บนเดสก์ท็อป (สองเวอร์ชันล่าสุด)

## Look & feel (บังคับกรอกถ้ามีหน้า UI)

### ผู้ใช้และบริบท
- พนักงานเปิดบนมือถือระหว่างเดิน หรือเปิดบนเดสก์ท็อปที่โต๊ะ วันละ 1–3 ครั้ง ต้องการคำตอบว่า "ห้องไหนว่างตอนนี้" ภายในไม่กี่วินาที แอดมินเปิดบนเดสก์ท็อปสัปดาห์ละไม่กี่ครั้ง

### ความรู้สึกที่ต้องการ (เลือก 3 คำ) และที่ไม่เอา
- อยากได้: สะอาด · เป็นกันเอง · อ่านเร็ว
- ไม่เอา: ราชการ · ตารางแน่นเหมือน Excel · สีฉูดฉาด

### เว็บ/แอปอ้างอิง
- Google Calendar: มุมมองรายวันที่แต่ละห้องมีสีของตัวเอง
- Cal.com: หน้าเลือกเวลาที่ใหญ่ชัด แตะง่ายบนมือถือ
- Linear: ความสะอาด เส้นบาง พื้นที่ว่างพอดี

### ไม่อยากให้เหมือน (anti-reference)
- ระบบจองห้องแบบ intranet เก่าที่เป็นตารางสีเทาเต็มหน้าและปุ่มเล็ก

### ลำดับความสำคัญของหน้า (หน้าไหนต้องสวยที่สุด)
1. ตารางห้องรายวัน (หน้าแรก)
2. ฟอร์มจอง (บนมือถือ)
3. การจองของฉัน

### สี / ฟอนต์ / โลโก้ (CI)
- **สีหลัก (CI):** ให้ AI เลือก (เสนอ 3 แบบ)
- **สีรอง:** ให้ AI เลือก
- **สีตกแต่ง (accent):** ให้ AI เลือก
- **โลโก้:** ไม่มี
- **ฟอนต์:** ให้ AI เลือก (ไทย)
- **ปรับเฉดเพื่อให้อ่านชัดได้ไหม:** ได้
- **สีประจำห้อง:** A ส้ม · B ฟ้า · C เขียว (ใช้สีเดียวกันทุกหน้า แยกจากสีแบรนด์)
- ธีม: ตามระบบ พร้อมปุ่มสลับ

### ความหนาแน่นข้อมูล
- ปานกลาง: ตารางรายวัน 3 ห้อง × 20 ช่อง ต้องเห็นครบทั้งวันในจอเดียวบนเดสก์ท็อปโดยไม่เลื่อน

### ภาพรวมที่ต้องมี
- หน้า "การใช้ห้อง": กราฟแท่งเปอร์เซ็นต์การใช้งานรายห้องรายวัน (จันทร์–ศุกร์) และโดนัทสัดส่วนชั่วโมงที่ถูกจองแยกตามห้อง ใช้สีประจำห้องเดียวกับตาราง

### ข้อมูลตัวอย่างสำหรับดูหน้าจอ
- พนักงาน 25 คน (ชื่อไทยสมจริง ยาวสั้นปนกัน) แอดมิน 2 คน · 3 ห้อง ตามกฎธุรกิจ (มีห้องหนึ่งถูกปิดใช้งานชั่วคราวในข้อมูลชุดที่สอง) · การจองประมาณ 60 รายการในสัปดาห์นี้และสัปดาห์หน้า รวมการจองซ้ำรายสัปดาห์ การจองที่ต่อเนื่องกันพอดี (ไม่ชน) หัวข้อประชุมยาว 100 ตัวอักษร วันหยุดบริษัทหนึ่งวัน และวันที่ห้องเต็มทั้งวัน

### เกณฑ์ผ่านด้านภาพ
- ตารางรายวันเห็นห้องทั้งสามและช่องว่าง/ถูกจองได้โดยไม่เลื่อนบนเดสก์ท็อป · ไม่มีข้อความล้นหรือทับกันที่ 390 px และ 1440 px ทั้งสองธีม · ฟอนต์ไทยที่เลือกโหลดจริง · สีประจำห้องแยกแยะได้โดยไม่ต้องพึ่งสีอย่างเดียว (มีชื่อห้องกำกับ)

## Tech stack & ข้อจำกัด ★
- **ต้องใช้:** ใช้ค่าเริ่มต้น (`stack.md`: monorepo Next.js + NestJS + Prisma + PostgreSQL + Docker, shadcn/ui)
- **UI kit:** ไม่ใช้ (ใช้ shadcn/ui ตามค่าเริ่มต้น)
- **ห้ามใช้:** บริการคลาวด์ที่ต้องสมัครบัญชีหรือเสียเงินรายเดือน (เช่น Firebase, Supabase, Auth0) · Redis (เครื่องมี RAM จำกัด)
- **ของที่มีอยู่แล้วต้องต่อด้วย:** ไม่มี
- **Auth:** อีเมล + รหัสผ่านเท่านั้น (ไม่มี SSO) สิทธิ์สองบทบาท: พนักงาน และแอดมิน
- **Integration ภายนอก:** ไม่มี
- **ภาษาของ UI และเอกสารผู้ใช้:** ไทย วันที่แสดงเป็นปี พ.ศ.
- **ขนาดงาน:** ผู้ใช้พร้อมกันสูงสุด 25 คน · ข้อมูลโตราว 7,500 การจองต่อปี (30 ครั้งต่อวันทำการ × 250 วัน) ทดสอบด้วย 10,000 · ไม่มีไฟล์อัปโหลด
- **เบราว์เซอร์/อุปกรณ์:** Safari บน iPhone, Chrome บน Android, Chrome บนเดสก์ท็อป (สองเวอร์ชันล่าสุด) หน้าจอ 360–1440 px

## เซิร์ฟเวอร์และการ deploy ★
- **ปลายทาง:** Raspberry Pi 4 ในห้องเซิร์ฟเวอร์ของออฟฟิศ
- **สเปกเครื่อง:** arm64 · RAM 4 GB · SSD USB 128 GB · Raspberry Pi OS 64-bit
- **Docker:** ติดตั้ง Docker และ Compose plugin แล้ว (ลงอย่างอื่นเพิ่มได้ถ้าจำเป็น) ไม่มี container registry
- **เครือข่าย:** เฉพาะ LAN ในออฟฟิศ เข้าผ่าน `http://rooms.office.local` ด้วย **HTTP (ไม่มี HTTPS และไม่มีโดเมนสาธารณะ)** พอร์ต 80 เปิดใช้ได้
- **ใครดูแลและ deploy ยังไง:** ผู้พัฒนา 1 คน build image arm64 บนเครื่องตัวเอง ส่งขึ้น Pi ด้วย `docker save | ssh pi docker load` แล้ว `docker compose up -d` ไม่มี CI
- **Backup / secret:** `pg_dump` ทุกคืนเวลา 02:00 เก็บ 14 วันบน USB drive อีกตัวที่แยกจาก SSD หลัก · ไฟล์ `.env` อยู่บน Pi เท่านั้น ไม่เก็บใน git
- **งบ/ต้นทุน:** ไม่มีค่าใช้จ่ายรายเดือน

## การตัดสินใจที่ล็อกแล้ว (agent ห้ามเปลี่ยน)
- ชื่อ ความจุ และอุปกรณ์ของห้องทั้งสาม · ช่วงเวลาละ 30 นาที · เวลาทำการ 08:00–18:00 จันทร์ถึงศุกร์
- ใช้ PostgreSQL และ Prisma · ระบบต้องทำงานบน HTTP ธรรมดา (ห้ามพึ่ง API ที่ใช้ได้เฉพาะ HTTPS เช่น `crypto.randomUUID`)
- แสดงวันที่เป็นปี พ.ศ. · UI ภาษาไทยทั้งหมด

## ถ้าไม่แน่ใจ ให้ agent...
- ตัดสินใจเองแบบเรียบง่ายและจดไว้ใน `docs/DECISIONS.md` เสมอ ยกเว้นเรื่องต่อไปนี้ ให้ **ไม่ตัดสินใจเอง** แต่ใส่ใน Open questions เพื่อถามที่ Gate 1:
  - ตารางแสดงชื่อผู้จองให้พนักงานทุกคนเห็นหรือเห็นเฉพาะของตัวเอง (เรื่องข้อมูลส่วนบุคคล)
  - พนักงานแก้การจองของคนอื่นได้ไหมถ้าผู้จองลาป่วย (เรื่องสิทธิ์)
